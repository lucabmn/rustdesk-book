## Review

**Ergebnis: Blocker vorhanden.**

- **Blocker – Passwortverlust bei Wiederholung eines Single-use-Skripts:** Das Skript setzt zuerst ein neues Zufallspasswort (`src/lib/deployment-script.ts:105-127, 208-233, 291-317`). Bei einem erfolgreichen Enrollment mit verlorener HTTP-Antwort setzt ein Retry erneut ein anderes Passwort. Der Server behandelt denselben RustDesk-ID-Replay als idempotent, aktualisiert das gespeicherte Passwort aber ausdrücklich nicht (`src/lib/enrollment.ts:83-104`). Danach meldet das Skript Erfolg, während rustdesk-book das alte, ungültige Passwort enthält. **Vorschlag:** Enrollment als mehrstufiges/idempotentes Protokoll implementieren und Passwort bzw. Attempt-ID lokal geschützt wiederverwenden; niemals vor validierter Token-Claim ein irreversibles Passwort setzen.

- **Hoch – Fehlgeschlagenes Enrollment hinterlässt unbekanntes Gerätepasswort:** Alle Skripte ändern das RustDesk-Passwort vor dem API-Aufruf. Bei ungültigem Token, HTTP-Fehler oder Nichterreichbarkeit ist das neue Zufallspasswort nach Prozessende verloren (`src/lib/deployment-script.ts:105-127, 208-233, 294-317`). **Vorschlag:** Token zunächst serverseitig validieren/reservieren, Passwortänderung bestätigen und bei Fehlern rollbacken bzw. das Passwort bis zum bestätigten Abschluss geschützt persistieren.

- **Hoch – Unix-Skripte erkennen CLI-Fehler nicht zuverlässig:** Linux/macOS verwerfen die Ausgabe von `--config` und `--password` und vertrauen nur dem Exit-Code (`src/lib/deployment-script.ts:208-210, 293-295`). RustDesk kann etwa „Settings are disabled“ ausgeben, ohne einen Fehlerstatus zu liefern. Dann wird ein nie gesetztes Passwort enrollt. Windows prüft solche Meldungen bereits (`src/lib/deployment-script.ts:100-109`). **Vorschlag:** Ausgabe auch unter Unix erfassen, bekannte Fehlerzustände ablehnen und die erfolgreiche Passwortsetzung verifizieren.

- **Hoch – Bearer und Gerätepasswort dürfen über HTTP übertragen werden:** `baseUrl` akzeptiert jedes URL-Schema (`src/orpc/router/enrollments.ts:18-25`), und die Skripte übernehmen den Origin unverändert (`src/lib/deployment-script.ts:21-37, 132-144, 238-250`). Bei einer per HTTP geöffneten Installation werden permanenter Bearer und Gerätepasswort unverschlüsselt gesendet. **Vorschlag:** Serverseitig eine konfigurierte kanonische HTTPS-URL verwenden und HTTP nur explizit für Loopback-Entwicklung erlauben.

- **Hoch – Öffentlicher Endpoint puffert unbeschränkt große Chunked Bodies:** Die Größenkontrolle erfolgt erst nach `request.text()`, wodurch ein Request ohne vertrauenswürdiges `Content-Length` bereits vollständig im Speicher liegt (`src/routes/api.enroll.ts:24-33`). Der öffentliche Endpoint ist damit für Memory-DoS anfällig. Zusätzlich fehlt eine eigene Rate-Limitierung; jeder ungültige Token verursacht einen DB-Lookup (`src/routes/api.enroll.ts:47-54`, `src/lib/enrollment.ts:72-77`). **Vorschlag:** Body gestreamt mit hartem Limit lesen und IP-/Token-basierte Limits am Endpoint oder Reverse Proxy ergänzen.

- **Hoch – Auto-Installation führt ungeprüfte Downloads als root/SYSTEM aus:** MSI, DEB, RPM, Arch-Paket und DMG werden lediglich per HTTPS geladen und unmittelbar privilegiert installiert (`src/lib/deployment-script.ts:89-95, 176-203, 278-286`). Die Versionsnummer pinnt den Inhalt nicht kryptografisch. **Vorschlag:** Erwartete SHA-256-Werte serverseitig pinnen und prüfen; zusätzlich Authenticode, Paket- bzw. `codesign`/`spctl`-Validierung verwenden.

- **Mittel – Revocation ist für permanente Tokens nicht atomar wirksam:** Der konditionale Update prüft zwar `revoked_at IS NULL`, sein Ergebnis wird aber ignoriert (`src/lib/enrollment.ts:130-143`). Wird der Token nach dem initialen Select, aber vor diesem Update widerrufen, kann der Update null Zeilen treffen und das Gerät wird trotzdem eingefügt. Der Single-use-Replay aktualisiert ebenfalls ohne erneute Revocation-Prüfung (`src/lib/enrollment.ts:94-99`). **Vorschlag:** Tokenzeile sperren oder jeden konditionalen Update per `RETURNING` prüfen und bei null Zeilen abbrechen.

- **Mittel – Re-Enrollment mit neuem Token erzeugt Duplikate:** Eindeutigkeit gilt nur für `(enrollment_token_id, rustdesk_id)` (`src/db/schema.ts:164-167`, `drizzle/0001_nice_mauler.sql:24`). Dasselbe Gerät mit einem erneuerten Token wird daher als zweite Zeile mit möglicherweise anderem Passwort angelegt. **Vorschlag:** Eine kanonische Identitätsregel für RustDesk-IDs festlegen; entweder global eindeutig upserten oder einen bestehenden Fremd-Token-Treffer explizit mit `409` ablehnen.

- **Mittel – Jedes Mitglied kann permanente Deployment-Credentials ausstellen:** Create/List/Revoke verwenden lediglich `authed` (`src/orpc/router/enrollments.ts:28,65,94`), und die UI zeigt Enrollment unabhängig von `isAdmin` (`src/components/address-book/address-book.tsx:396-402, 838-842`). Damit kann jedes Konto dauerhaft öffentlich nutzbare Delegations-Tokens erzeugen. **Vorschlag:** Falls Client-Rollout eine administrative Funktion ist, `adminProcedure` verwenden und die UI entsprechend ausblenden; andernfalls diese weitreichende Rollenberechtigung ausdrücklich dokumentieren.

- **Mittel – Permanente Bearer werden leicht als Klartext hinterlassen:** Der Token steht dauerhaft im Skript (`src/lib/deployment-script.ts:34,141,247`); Downloads werden ohne Hinweis auf restriktive Dateirechte oder anschließendes Löschen angeboten (`src/components/address-book/enrollment-dialog.tsx:98-106`). Unter Unix erscheint er zudem als expandiertes `curl`-Argument im Prozesslisting (`src/lib/deployment-script.ts:226-233,310-317`). **Vorschlag:** Restriktive Dateirechte/Löschung deutlich anweisen, Header nicht über argv übergeben und für breite Rollouts kurzlebige bzw. rotierbare Tokens bevorzugen.

- **Niedrig – Migration erzwingt sicherheitsrelevante Invarianten nicht:** `kind` ist freier Text und `use_count` kann negativ sein (`src/db/schema.ts:110-118`, `drizzle/0001_nice_mauler.sql:6-14`). Jeder unbekannte Kind-Wert wird in der Registrierungslogik wie ein permanenter Token behandelt (`src/lib/enrollment.ts:106-143`). **Vorschlag:** DB-Checks für `kind IN ('single','permanent')` und `use_count >= 0` ergänzen.

- **Niedrig – Token kann durch versehentliches Schließen unwiederbringlich verloren gehen:** Escape/Close setzt den einzigen Klartext samt Skripten sofort zurück (`src/components/address-book/enrollment-dialog.tsx:111-117, 360-368`). Der Token bleibt danach aktiv, ist aber nicht mehr abrufbar. **Vorschlag:** Vor dem Schließen bestätigen lassen oder erst nach bestätigtem Kopieren/Download schließen; alternativ direkt Revocation anbieten. Die Plattform-/Aktionsleiste sollte außerdem umbrechen, da sie auf schmalen Viewports ohne `flex-wrap` horizontal überläuft (`src/components/address-book/enrollment-dialog.tsx:146-163`).
